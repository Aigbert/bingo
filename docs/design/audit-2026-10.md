# Architecture audit — 2026-10-13

> Asked by the user before an architecture upgrade: where are the biggest
> problems, and could bingo host something like Claude Code's mods? Five
> read-only audits (kernel, TUI, feature plugins, external boundaries,
> composition and tests) at `979a6d27` (v0.6.6); the load-bearing claims
> were re-read in the source. **[inferred]** marks a claim read from the
> code but not reproduced. The work this leads to is in
> [upgrade-2026-10.md](upgrade-2026-10.md); line numbers are as of the
> audited commit and drift.

## The verdict in two sentences

The crate graph is clean: no plugin imports another, the kernel imports no
plugin, and `scripts/check_discipline.sh` holds that. But the coupling the
graph forbids did not disappear — it moved into string ids, hand-copied
record shapes and copied mechanism, where the compiler cannot see it; and
the journal does four jobs at once (persisted format, wire, working memory,
the model's context source), so every cost grows with a session's age.

Scale: ~216k lines of Rust in 34 crates (TUI 49.7k, core 27.8k, channels
14.5k, provider-acp 10.9k, rooms 9.9k). `fix(…)` commits since August:
tui 38, core 21, channels 10, bin 9, agents 7.

## 1. The journal is unbounded, unversioned, and folded three ways

**Working memory.** The actor keeps every durable frame in
`journal: Vec<Frame>` (`bingo-core/src/session.rs:62`); each turn starts
with `history: actor.journal.clone()` (`session/running.rs:41`) and
re-reads it from frame 1 in `ContextView::items` (`context.rs:22`), whose
`iter().find` upsert is O(n²). Resume reads the whole file
(`host/resume.rs:80`); `mid_turn` reads every child's whole journal to see
whether it is busy (`resume.rs:156`). `SessionStore::replay` returns a
`Vec`; nothing streams, nothing is checkpointed. Plugin state is re-saved
whole at the head of every process-life segment (`session.rs:284`).
Compaction shortens the prompt and makes nothing else cheaper.

**Three reducers over one journal.** `SessionState::apply`
(`bingo-sdk/src/state.rs:175`), `ContextView::items` (core) and the turn's
own `self.items` (`turn.rs:322-330`, `splice_compaction` at `turn.rs:791`).
They already disagree: `SessionState` withdraws the items a
`TurnRetrying { dropped }` names (`state.rs:192`, `turn_retrying`);
`ContextView::items` has no arm for it. `TurnRetrying` is durable, so the
withdrawn half-answer of a failed attempt is very likely sent again in
every later turn's request and after every resume **[inferred — the turn
test `a_retryable_error_withdraws_the_attempt_and_tries_again` checks only
the retry inside the same turn]**.

**The persisted format is the live type.** The header says `VERSION = 1`
(`bingo-store-jsonl/src/journal.rs:17`); `event.rs` changed in 19 commits
since 2026-08-29, including removed variants (379bd04c, 4afd43d3) and a
restructured `Question` (6471cde6). No persisted enum has a catch-all, and
one unreadable line before the last fails the whole replay
(`journal.rs:118-140`, as ADR-0005 §3 decided for corruption — but an
unknown variant from a newer binary is not corruption). One compatibility
fixture exists: `bingo-core/fixtures/frames-v1.jsonl`, 16 lines, last
touched 2026-08-29. `PluginManifest.sdk` claims to be checked at boot;
nothing checks it (48 manifests say `^0.1`, the workspace is 0.6.6).

**Pictures.** Base64 inside `Item`s, so every clone above copies them.
ADR-0061/0062 bounded what is *sent*; the bytes still live in the journal
and in memory (ADR-0005 §8 deferred blobs to "version 2"). The 1 MB bound
is applied by six producers separately (tool-fs, mcp, tool-web, channels,
tui, print) and missed by plugin-rpc tool output
(`bingo-plugin-rpc/src/tool.rs:188`). Nothing bounds a whole request: five
unrelated limits (5 MB per image at input, 1 MB per picture, 3 rounds kept,
text truncation, overflow elision) and an estimator that counts every image
as a flat 1 600 tokens (`tokens.rs:24`).

**Direction.** One sdk fold that yields both the client's view and the
model's; the turn applies its own frames through that fold. A versioned
persisted record with an unknown-variant arm and golden fixtures. A
checkpoint at compaction and a cold replay that starts from it. Picture
bytes in blobs. A kernel ceiling per picture and per request.

## 2. Plugin isolation moved the coupling into strings

**The TUI parses eight plugins' private records by id** — `seats.rs`
(`"bingo.rooms"` and ~20 field names), `tasks.rs` (`"bingo.tasks"` and four
tool names), `shells.rs` (`"bingo.tools.bash"`), `wake.rs`
(`"bingo.schedule"`), `memory.rs` (`"_bingo.context"`), `permission.rs`,
`acp.rs` ("copied from `bingo_provider_acp::events`"), `skill.rs`, and
`input.rs:43 PROMOTE`. ~3.4k production lines and ~950 lines of screen
tests, no fixture shared with any producer. The generic ADR-0013 lanes grew
per-plugin exceptions: `panel.rs:45 !tasks::is_list`, `rail.rs:82
!shells::is_set`, `transcript.rs:154/421/761`, `blocks.rs:92`. Every
feature milestone grows the TUI.

**Agents and rooms are one feature in two crates.** The `#room` write path
lives in agents (`message.rs:150-190`, `serial.rs`); `PARENT`, signing and
the name check are each written twice (agents `names.rs`, rooms
`name.rs`), and a third time in `tui/seats.rs:31`. **Names compare
differently:** rooms `name::same` lowercases both sides (`name.rs:15`);
agents `free`, `named` and the `PARENT` check compare exactly
(`names.rs:28, 208, 46`), so `Scout` and `scout` can both be spawned while
rooms treats them as one member with one cursor, and an agent may be named
`Parent`. Both manifests declare `requires: &[]` though each needs the
other; the one service between them is a string key, a method name and
JSON (`agents team/service.rs:33`, `rooms team.rs:27`).

**Untyped seams elsewhere.** Services are `HashMap<String, Arc<dyn Any>>`
with a downcast (`bingo-sdk/src/host.rs:661`): a key/type mismatch is a
runtime `None`. `SurfaceOptions.args` is a JSON object whose eight keys are
written in `crates/bingo/src/main.rs:806-823` and read back by name in
print, rpc and tui. The bin re-declares plugin schemas (`bingo/src/mcp.rs`
re-spells `"bingo.mcp"`/`"mcpServers"`; `provider.rs:170-210` writes the
providers' instance shape). Prompts name tools without any check that they
are registered (`agents spawn.rs:210`, `provider-acp offer.rs:32`).
`is_internal_extension` hard-codes `"bingo.context"` in the sdk
(`event.rs:24-28`).

**Direction.** `ServiceKey<T>` and declared requirements; shared nouns in a
library both plugins depend on; plugins place their own views (slots), so
the TUI parses no plugin record; typed surface options.

## 3. Cancellation and deadlines work where someone remembered them

`racing()` (`turn.rs:133`) wraps 18 awaits. Not wrapped: `hooks.gather()`
(`turn.rs:798`), `gate_call` (`turn.rs:823`) and so all eight awaits in
`gate.rs` — before-tool hooks (`:117`), `policy.decide` (`:130`), the
permission prompt (`:162`) — and `compactor.compact` (`turn.rs:736`).
Non-instant commands run in a detached `tokio::spawn` with no handle and no
token while holding the input queue (`session/commands.rs:188-259`);
`interrupt` with no turn running answers `NotReady` (`inputs.rs:240`), so a
hung command blocks the session and esc cannot reach it. The actor performs
store appends inline (`session.rs:577`; the JSONL store does synchronous
`std::fs` open/write/flush per frame), and **a failed append is logged and
the frame is broadcast anyway** — "journal first" (ADR-0002 §2) is not
enforced. The mailbox is unbounded. MCP tool calls, plugin `tool/call`, a
held ACP prompt and the codex token refresh (`openai/lib.rs:120`, a bare
`reqwest::Client::new()`) have no deadline; the plugin provider's idle cut
is 120 s, the HTTP providers' 300 s. Four in-memory timers each implement
"wake session S after D unless X" (rooms `chase.rs`, rooms `deadline.rs`,
schedule `wakes.rs`, agents `watch.rs`); the background report-back is a
detached spawn (`agents spawn.rs:402`) lost on restart **[inferred]**. The
esc-latency bug (774 ms to 51 s) belonged to this class and was fixed one
await at a time.

**Direction.** Turns and commands are supervised tasks with tokens, and the
cancellable part of a turn is one future dropped at the top. Store writes on
a writer task whose failure stops the session. A kernel deadline policy.
One durable delayed-delivery primitive.

## 4. TUI: layout is a side effect of drawing

`view::draw` writes `ui.painted` (a `RefCell`) in 17 places and input reads
the previous frame's `Painted` (21 references in `input.rs`, 9 in
`pointer.rs`); measuring calls the renderers, so several bands are laid out
twice a frame. Layout and row maths are the largest group of `fix(tui)`
commits (11 of 38). The session-tree fold is written three times —
`tui/tree.rs:83`, `channels/runner.rs:48`, `print/lib.rs:213`, each a
`BTreeMap<SessionId, SessionState>` — and the TUI keeps a second map of
handles beside it (`run.rs:108`). Focus is ~10 flags tested in a fixed order
in `on_key` (`input.rs:45`) and a different order in `pointer::on_mouse`.
`Run::animating` ORs 12 conditions; the block cache's `Revision` has 11
keys; theme and graphics detection are process globals with 19
`cfg(not(test))` twins, so production detection never runs under test.

**Direction.** `TreeState::apply` in the sdk; a pure `layout()` pass that
both drawing and hit-testing read; one `Focus` state; an explicit render
context; `next_frame: Option<Instant>` returned by the view.

## 5. Mechanism is copied instead of shared through the library tier

The anthropic and openai `metered.rs` are byte-identical but for comments
(266 lines each); with `sse.rs`, `stream.rs`, `key.rs` and the transport
test harness, ~1.4k lines exist twice (ADR-0056 §5 chose this: "two copies,
one record"). Three JSON-RPC stdio stacks (~2k lines: surface-rpc, plugin-rpc
— "deliberate" copy, `codec.rs:4-6` — and provider-acp). `shell()` twice
(`tool-bash/run.rs:62`, `hooks-shell/run.rs:33`, "spelt twice"); process-tree
spawning three times (bash, acp `child.rs`, hooks-shell), and missing for
MCP stdio servers (`mcp dial.rs:174-182`) and plugin processes
(`plugin-rpc connection.rs:268-279`), so an `npx` launch likely leaves
grandchildren **[inferred]**. Four claim styles: store `try_lock`, schedule's
OS lock (M106), gateway pidfile, and channels `create_new` removed only in
`Drop` (`channels/lock.rs:30-44`) — **stale after a kill**, the bug M106
fixed for schedule alone. Schedule and experience share a copied file store
and `id.rs`; `diff.rs` exists three times. Channels adapters are a closed
list: adding a platform edits ~6 places that name `feishu`.

**Direction.** Library crates (ADR-0012 §1, ADR-0042 §2 already allow
them): `bingo-http`, `bingo-process`, `bingo-jsonrpc`, a claim, a file
shelf; an adapter registry for channels.

## 6. ACP is a stateful agent behind the stateless `Provider`

~5.6k production lines, more than anthropic and openai together: its own
session map, child lifecycle, restore ladder, knobs machine, permission
questions and MCP bridge. The kernel grew `HostApi::invoke` for it, and
`ModelRequest.session` and `holds_context` to fit it; the kernel still
builds the full history every round and ACP throws all but the last user
message away. The agent's own tool calls arrive as reasoning blocks with
metadata (`provider-acp/src/events.rs:1-21` admits the departure from
ADR-0035 §4), so the gate, `BeforeTool` hooks and `/rewind` checkpoints do
not see its edits **[inferred]**. It advertises images and sends text only
(`provider.rs:165-175`, `:207-211`, `:278`): pasted pictures are dropped.

**Direction.** Split the seam: a stateless `Provider` (full context in) and
an `Agent` (newest turn in; events that include tool calls already run
elsewhere), so the kernel can show, observe and checkpoint them.

## Bugs that do not wait for the upgrade

1. `ContextView::items` ignores `TurnRetrying` [inferred; the test comes
   first].
2. A failed journal append is still broadcast.
3. The channels claim is stale after a kill.
4. Agents and rooms compare names under different case rules.
5. ACP drops pictures it advertised it accepts.
6. plugin-rpc tool output skips the picture bound.
7. Windows Bash tool and shell hooks spawn `/bin/sh`.

All but the first were confirmed in the source.

## What is fine and should stay

The dependency graph and its check; `Event` (22 variants) and `ItemBody`
(13) are small; bounded per-subscriber channels with lag-and-resync; retry
and backoff in one place (`turn/stream.rs`); tool properties that fail
closed; tool-bash's internal shape; channels as a true client of
`SessionState::apply`; pure `on_key`/`on_mouse` returning `Effect`;
`frame::regions` and `window.rs`; `TestBackend` coverage; the pinned wire
snapshot.

## Mods: what Claude Code has, what bingo has

**Claude Code mods** (read from its plugin-authoring reference and types):
a module calls `on(event, matcher, ($, e, next) => …)`. Every one of ~80
events is a middleware chain with the engine's own behaviour at the bottom:
a hook may pass, rewrite (`next({...e})`), answer for itself, or
`await next(e)` and act on the result — and the `$` calls themselves
(`tool.call`, `fs.read`, `http.fetch`, `model.complete`, `prompt.compose`,
`session.append`) are events too. UI: `ui.render` hooks on named components
(`AbovePrompt`, `Pane`, tool rows, messages, `CommandOutput`) with an
element table per surface and the engine's own drawing as fallback, plus
status and toast. State: host-held versioned `$.state` atoms that subscribe
on read and survive reload, and `$.store` across sessions. A sandboxed
runtime with no Node: everything outside goes through `$` (tools, commands,
agents, model calls, prompt submission, timers, processes, fs, http). Hot
reload on save; generated `.d.ts` contracts; `claude plugin validate/test`;
a marketplace.

**bingo has about half.** plugin-rpc (ADR-0015, 0030–0032) carries tools,
commands, contributors, compactors, providers, services and hooks across a
process boundary in any language; `PROTOCOL = 1`. ADR-0013's view
vocabulary and three lanes, with a text fallback for print and IM — wider
than Claude Code's terminal-first elements; Pages (ADR-0054), switches
(ADR-0057). The `Hook` trait has eight fixed points (Submit, BeforeTool,
AfterTool, Stop, Turn, Compact, Session, Event) and enum outcomes
(Continue, Deny, Ask, Block, Redirect); ADR-0032 §4 lets an external hook
only tighten.

**Gaps, in dependency order.**

1. *Interception.* A chain at every dispatch point with the kernel's
   behaviour at the bottom — the same refactor §3 asks for — plus a trust
   ADR: may a user-installed mod rewrite or loosen?
2. *UI placement.* Plugins can fill their own lanes but cannot occupy a
   band, pane, status entry or rail; the TUI hard-coding eight first-party
   plugins shows the API is not enough even for first-party work. Same work
   as §2.
3. *Host state.* Signals are close to `$.state`; they lack a version,
   subscribe-on-read and a persistent store.
4. *Host capabilities.* A plugin process can only `service/call`: no model
   call, no agent spawn, no session submission, no timers, no runtime tool
   registration.
5. *Author kit.* No hot reload, no typed author SDK, and a protocol pinned
   at 1 while it changes in place — it must be frozen and versioned before
   the first outside plugin.

**Recommendation.** Keep the out-of-process JSON-RPC base; do not embed a
JS engine (V8 or deno_core would break the dependency and size budgets).
Do not pull a plugin's rendering every frame across a process boundary:
the plugin pushes the view for a slot as a Signal and the surface folds it —
the same effect as Claude Code's redraw-on-write, inside ADR-0002's one
stream. Generate a TypeScript author SDK from the committed schema, with
`on`/`next` as a thin layer over protocol 2. **Mods are the upgrade's
acceptance test, not a separate feature:** when §1–§3 are done the platform
is mostly there, and first-party plugins moving onto slots and interceptors
prove the API before anyone outside uses it.
